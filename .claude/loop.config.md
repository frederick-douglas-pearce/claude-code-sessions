# Loop config — claude-code-sessions

Per-project bindings for the supervised dev loop. `loop-engine.md` (the generic engine, bundled in
the plugin) references every value below **by parameter name**; this file is the only surface a
porting project edits. A non-matching (non-Python / non-`src/` / non-GitHub) project revises **all
four sections** (parameters, architect triggers, source layout, security routing) — never the
engine.

See `${CLAUDE_PLUGIN_ROOT}/skills/dev-loop/loop-engine.md` for the operating procedure and semantics.

> ⚠ **Generated by `/init-loop` — review before the first run.** Values are best-effort inferences;

## 2. `ARCHITECT_TRIGGERS`

Fire `DESIGN_AGENT` (`architect`) when the plan touches any of the following. Bias toward calling
it; this repo's blast radius is asymmetric (a bad sanitizer change leaks PII into a public repo).

- **Any change to the sanitizer's scrubbing behavior** — `tooling/sanitizer/src/ccs_sanitize/`
  rules, pipeline, residual scan, or sidecar shape. These carry a published determinism contract
  and a PyPI audience.
- **Anything that changes what a `.scrubbed` sidecar records**, or the fixture contract that
  `fixtures/sanitized/` and `fixtures/synthetic/` depend on.
- **Changes to `.claude/hooks/`** — `block_secret_reads.py` / `detect_secrets_in_output.py` are the
  live-session guards; a weakened matcher is a silent loss of coverage.
- **A new reference-doc contract** that AgentFluent or CodeFluent will link to (a field definition's
  meaning, a format-version-history entry) — these are cross-repo interfaces.
- **CI/workflow structure changes**, especially anything touching the required `sanitizer-ci` gate
  or the `sanitizer-v*` release path.
- **The orchestrator is unsure.**

Skip for: post drafting and copy edits, `reference/` prose that documents an already-verified field,
social drafts, and typo fixes.

## 3. `SOURCE_LAYOUT` — router signals

- **Package layout:** Python lives under `tooling/`, in four independently-tested units:
  - `tooling/sanitizer/` — installable package (`src/ccs_sanitize/`, tests in
    `tooling/sanitizer/tests/`, its own `pyproject.toml`). The only unit that ships.
  - `tooling/format-scan/` — `scan.py` + `tests/` (a package, has `__init__.py`).
  - `tooling/` root helpers — `publish-to-pages.py`, `check-og-cards.py`, tests in `tooling/tests/`.
  - `.claude/hooks/` — guard hooks + `tests/test_hooks.py` (stdlib `unittest`, not pytest).
  - `tooling/fixture-validator/` is **README-only** — planned, not built. A change there is
    `stub-defer` until the validator exists.
- **`docs` label / path:** label `documentation`; paths `posts/`, `reference/`, `social/`,
  `README.md`, `CLAUDE.md`, `SECURITY.md`. Per CLAUDE.md these may go **direct to main** — no PR,
  no branch. **Exception:** a *material* multi-file doc catch-up (correcting stale status/claims
  across several files) goes via issue + PR for posterity.
  > ⚠ **That direct-commit policy governs *humans*, not the loop.** A routed issue always goes
  > through the engine's commit + PR step, whatever its route — the loop must never bypass its own
  > gates. Skipping the PR would not just skip a formality: it removes the artifact the code-review
  > and merge gates operate on, so the row would reach `done` with no gate having run on it and no
  > merge gate at all, and the ledger would look identical either way. If this policy and the
  > pipeline ever appear to conflict, **the pipeline wins**. (See claude-code-loop#1, F91.)
- **`research` label / path:** label `research`; path `.claude/specs/research/` (the format-watch
  queue). No test-coverage gate. `.claude/specs/` generally is planning/PRD territory.
- **`stub-defer` marker:** an issue whose title begins **`Epic:`** or **`Coordinating PR:`** —
  tracking-only umbrellas that are not directly implementable. Currently #3, #5 (`Epic:`) and #10,
  #11 (`Coordinating PR:`). The loop does **not** close these; they close when their children do.
  **Note the correction:** the `(blocked — …)` parenthetical the generator cited (#155, #55) is a
  **Status** signal, not a Route — those rows are `blocked` on an unmet dependency and keep their
  real route. Route and Status are separate columns; conflating them would send implementable work
  to `stub-defer` and strand it. No `blocked` label exists in this repo, so that status is carried
  in the ledger's Status column and the title parenthetical is the human-readable echo.
- **`code` (default):** bug/enhancement touching `tooling/`, `.claude/hooks/`, `.github/`, or
  `fixtures/` → full pipeline, **PR required** (CLAUDE.md §"Branching & PR workflow" makes this
  explicit: those four are the code/infra and data surfaces with blast radius).

## 4. Security routing

This repo documents a format that carries secrets, so security routing is not a formality here.
CLAUDE.md §"Security posture" and §"Security gate" are the substantive spec; this section is the
loop's binding to them.

- **Every PR and every direct content commit** must confirm the two diff-level invariants: **no raw
  session JSONL committed** (only synthetic fixtures, or sanitized fixtures with a `.scrubbed`
  sidecar), and **no secrets** in fixtures, posts, or examples. The `.claude/hooks/` guards cover
  live sessions, not diffs — the diff-level check is the loop's job.
- **Run the local `/security-review`** when the diff touches any of: `tooling/sanitizer/`,
  `.claude/hooks/`, `fixtures/`, `tooling/publish-to-pages.py`, path/JSONL parsing, or
  `.github/workflows/`. That list is the PR template's own "Closer read done if..." row.
- **There is no labeled security workflow to trigger** — unlike a repo that applies a
  `needs-security-review` label at dev-complete, this repo has no such label and no such workflow.
  The local skill plus the human-attested PR section are the whole gate.
- **Never read from `~/.claude/projects/`** to illustrate anything; read from `fixtures/`. And never
  read the live sanitizer config — the PreToolUse hook denies it, and it holds literal PII. The
  committed `.example` template is the PII-free reference.
- Skip for docs/no-surface changes (a post typo, a reference wording fix).

### ⛔ Precondition — `origin/HEAD` must be set, or the local review gate dies before it runs

**Git-specific, not host-specific** — unlike §4's routing rules above, this needs only git and a
remote named `origin`, and applies on any git host. *You*, reviewing this config, may delete it if
this project does not use git, names its remote something else, or binds `SECURITY_REVIEW` to
something that does not diff against `origin/HEAD`.

`/security-review` opens by diffing against `origin/HEAD`. When that ref does not resolve, the gate
exits with `fatal: ambiguous argument 'origin/HEAD...'` and reviews nothing.

**When it is absent — the rule, not a list of cases.** The ref is set only if the remote's own default
branch was among the refs your clone actually fetched. An ordinary full clone fetches it. It is
**absent** after a `--single-branch` or `--depth` clone of some *other* branch or a tag (the usual CI
checkout), a `--bare`/`--mirror` clone, a `git init` + `git remote add` + `git fetch`, or a clone of a
then-empty repo. It can instead be **dangling** — present but pointing at a branch the upstream has
renamed or deleted — which fails the same way. The check below tests that the ref *resolves*, so it
covers both.

**Repair.** These commands act on **the current directory**, so confirm where you are first — run
from the repo root:

```bash
git rev-parse --show-toplevel
GIT_TERMINAL_PROMPT=0 git remote set-head origin -a
git rev-parse --verify -q refs/remotes/origin/HEAD || echo "still unresolved -- see below"
```

`set-head -a` makes a **network call**: it can hang on an unreachable remote (interrupt it), and
`GIT_TERMINAL_PROMPT=0` suppresses git's own credential prompt but not `ssh`'s. If it reports
`Not a valid ref` or `Cannot determine remote HEAD`, your clone never fetched the remote's default
branch — fetch that branch first, then repeat:

```bash
git fetch origin '<default-branch>:refs/remotes/origin/<default-branch>'
```

**An erroring gate is not a passing gate.** Treat `fatal: ambiguous argument` from this gate as a
missing ref, not as a clean review: repair it and re-run. Never journal it as clean.
